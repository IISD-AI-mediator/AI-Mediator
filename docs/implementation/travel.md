# TRIP-01 · 여행 조율 구현 기준

기준은 `main`의 `0959e8e`와 French Toast 1.1.1(`330f872`)이다. 과제 PDF 2~3쪽은 Python·LangGraph, 복수 AI 모델과 외부 도구, 분기와 반복, 실제 시연을 요구한다. 7~9주차의 상태·조건 분기·메모리·병렬 처리, 11주차의 조정자·다중 에이전트 패턴을 적용한다. 원본 수업 PDF는 수강생용 로컬 자료다.

## 품질과 경계

1. **정확성과 복구**가 우선이다. 중복 제출과 재접속은 방·발언·최종 결정의 수를 바꾸지 않는다. 원래 확정된 항목을 서버에서 보호하고, 과거 라운드와 현재 결정을 함께 보존한다.
2. **권한과 사용성**이 뒤따른다. 초대 링크만 가진 방문자는 팀원 자격이 필요한 데이터에 접근할 수 없다. 각자의 추가 요청은 본인의 세션으로만 보낸다. 360px 화면과 키보드에서 방 생성부터 결과까지 진행할 수 있다.
3. **운영 비용과 관찰 가능성**을 확인한다. 약 20회 내부 시험을 전제로 단일 인스턴스, 방 정원과 실행 횟수 상한, 비공개 서버 환경변수, 지속 저장소를 사용한다. 검색 근거에는 출처와 조회 시점, 확인할 수 없는 정보에는 상태를 표시한다.

브라우저 → Python HTTP API → 방 저장소·실행기 → LangGraph 생성자/개인 조율자(검색 서브그래프)/결정자 → Gemini 및 외부 검색으로 연결한다. 모델 호출은 DB 잠금 밖에서 수행하고 중복 실행과 오래된 결과의 덮어쓰기를 방지한다. 단일 서비스와 분리된 워커 중 운영비와 복구 부담을 비교해 단일 서비스를 선택했다. [ADR-001, ADR-002](../adr/travel.md)

## 구현과 판정

| ID | 실제 호출 경로와 기대 동작 |
| --- | --- |
| AC1 | `/`의 인사 애니메이션·사용법과 방 생성 → 닉네임·정원·항목별 맡김·고정 계획·중재자 페르소나 → 생성자가 방 초기 조건으로 개인 에이전트 자리를 만든다. 재시도 시 중복 생성과 비용 지출을 제한한다. |
| AC2 | 방장이 복사한 `/r/<초대>` → 각자 닉네임·개인 요구 및 우선도·페르소나 → 고정 항목을 음영·읽기 전용으로 표시하고 서버에서도 수정 요청을 거절한다. 방장도 동일한 준비 절차를 거친다. 정원이 차고 전원이 제출해야 조율이 한 번 시작된다. |
| AC3 | 생성된 개인 조율자들이 병렬로 요청을 해석하고, 필요할 때 검색 에이전트가 실제 외부 검색을 수행해 URL·시점·결과를 돌려준다. 항공 최저가는 검증할 수 있는 경우만 표기한다. 결정자는 다른 모델로 잠정 결정을 기록·수정한다. |
| AC4 | 합의 시 결과, 갈등 시 파이트 모드로 분기한다. 참여자에게 알림을 주고 에이전트 발언을 그룹 채팅에 순차 표시한다. 열린 입력창 동안 본인에게 준 지시는 발언·판단 전에 반영된다. 닫힐 때 수락된 지시가 유실되지 않는다. 재연결로 같은 알림·발언을 중복하지 않는다. |
| AC5 | 중요한 제약과 근거로 중재하고 라운드를 제한한다. 합의, 고정 사항, 양립 불가능·확인 필요를 구분해 지속 저장한다. 오류에서 재시도하고 다른 방·참가자 자격의 요청을 거절한다. |
| AC6 | 3.13의 `iisd`, Windows 실행, 실제 그래프에서 생성한 이미지, 한국어 README, 기능별 Git 커밋, 팀용 URL, 버전 태그와 GitHub Release를 실제 상태로 검증한다. |

모델과 검색을 대체한 회귀시험은 별도 분류한다. 실제 모델·호스팅·브라우저·태그는 각각 성공 응답이나 실제 관찰로 판정한다.

## 동시성과 재시작 계약

브라우저는 생성·참여를 최초 요청 전에 저장한 임의 키로 재전송한다. 지시에는 별도 요청 ID를 붙인다. 동일 키의 성공 응답이 유실되면 기존 방·참가자·지시 번호를 돌려준다. 마지막 준비와 첫 실행 단계의 등록을 같은 DB 트랜잭션에서 수행한다. 실행기는 미완료 방의 단계, 턴 번호와 만료 시각을 가진 작업 임대를 획득하고, 외부 호출 후 해당 임대의 소유권과 단계가 일치할 때만 결과·고유 이벤트·다음 단계를 한 번에 기록한다. 시작할 때와 주기적으로 만료된 임대를 재개한다. 외부 호출 직후 프로세스가 종료되면 호출 비용이 한 번 더 들 수 있다. 공개 발언과 결정에는 동일한 단계 ID를 한 번만 기록한다.

파이트 모드에는 실제 사용자에게 적어도 20초의 열린 입력 시간을 준다. 수락한 지시마다 참가자별 증가 번호를 발급한다. 발언 생성 중 도착한 지시가 있다면 수신자가 해당 번호까지 처리할 다음 턴을 쓴다. 마지막 입력 창을 DB에서 원자적으로 닫고 마감 번호를 정한다. 닫힌 뒤의 요청은 즉시 거절한다. 닫히기 전에 수락한 지시는 발언 저장과 동시에 처리 완료로 기록하고, 모두 소진한 뒤 결정자를 호출한다. 폴링으로 양쪽 화면에 열린 시간·마감·전달 상태를 구분한다.

## 모델과 근거 계약

개인 조율·검색 질의는 `gemini-3.1-flash-lite`, 제3자 결정·최종 정리는 `gemini-3.8-flash`를 기본값으로 쓴다. 서칭 에이전트에는 여행지·날짜·출발지·시간대·숙소 위치 등 해당 질의에 필요한 최소 맥락을 준다. 실제 검색 결과에서 URL과 조회 시점을 보존하고, 항공편은 노선·날짜·시간대·통화·운임 조건을 확인할 수 있을 때만 관찰 가격으로 표시한다. 검증할 수 없는 최저가나 빈 검색은 확인 필요로 남긴다. 식당 검색에는 숙소 위치와 음식 종류를 포함한다. 검색 실패가 합의로 변환되지 않도록 한다.

저장 직전 서버가 방장이 확정한 항목을 원본에서 다시 적용한다. 상충하는 필수 조건은 강제 합의할 수 없고, 개인별 필수 조건·예산 상한·접근성·검증된 근거를 단순 선호보다 우선한다. 중재자의 말투는 공개 대화 표현에만 쓴다. 같은 조건을 두 페르소나로 제시해도 조건 판정은 같다. 각 잠정 값과 이유는 회차별로 남는다. 독립 시험에서는 동시 마지막 제출, 호출 전후 재시작, 마지막 턴 지시 경합, 다른 통화·노선의 가격, 모델의 고정 값 변경, 두 실제 모델의 응답을 구분해서 확인한다.

## 입력 형식과 팀 배포

AC1·AC2에서 중재자와 개인 에이전트는 각각 공격성·예의·MZ력 0~10 슬라이더와 자유 말투 입력을 갖는다. 기준값 5를 쓸 수 있다. 기존 저장 데이터의 프리셋 문자열도 계속 읽는다. 말투는 파이트 발언에 적용하고 판단의 근거에는 넣지 않는다. 1인 예산은 통화와 함께 범위 슬라이더, 정확한 금액 입력을 제공한다. 장거리 이동과 별도로 현지 교통수단(택시·대중교통·렌터카), 이미 예약한 항공편·일정을 지정할 수 있다. 참여자에게 고정 항목과 값은 회색 읽기 전용으로 보인다. 파이트 진입 시 화면 알림과 사용자 상호작용 후 브라우저가 허용하는 소리 알림을 제공한다.

슬라이더는 1인 최대 금액 **하나**를 고른다. 예약된 항공편은 가는 편과 선택적 오는 편의 편명·출발도착 공항·현지 일시를 입력하거나 일정 전체를 명시적으로 기입할 수 있고 고정 시 보존한다. 일자별 현지 이동에는 현지 교통수단을 쓴다. 생성자는 방 생성 요청 또는 그 트랜잭션이 등록한 즉시 실행할 작업에서 초기 고정 항목과 정원으로 참가자별 역할·임무를 만든다. 팀원이 들어오면 개인 입력과 연결한다. 전원 준비 전에도 실제 생성된 역할 정의가 저장되어야 한다.

Render는 `develop`의 Python 3.13 코드와 무료 PostgreSQL을 같은 리전에 배포한다. `feat/jinseo`의 변경은 PR로 통합하고 검증을 통과한 병합 커밋에 릴리스 태그를 붙인다. 방 생성은 팀 코드로 보호하고, Gemini 키는 서버 환경변수에만 둔다. 모의 응답과 공개 배포·실제 모델 확인은 테스트 결과에서 각각 식별한다.

## TRIP-02 · 판사 에이전트

기준 커밋은 `feat/jskim`의 `8eb4906`이다. [화면 흐름](../design/travel-flow.md)과 [ADR-003](../adr/travel.md#adr-003--두-모드의-판단과-최종-결정을-한-판사-에이전트에-맡긴다)을 적용한다.

우선순위는 전원 의견에 근거한 결정, 과거 방과 재시도의 일관성, 화면에서 화자와 모드를 식별할 수 있는 순서다. 기존 실행기·저장소·개인 모델과 판사 모델의 경계를 사용한다. 모델 실패는 기존 작업 임대 및 재시도 절차로 복구한다.

| 기준 | 호출 경로와 확인할 결과 |
| --- | --- |
| J1 · 조율 모드 | 전원 준비 → 좌석별 제안 → 판사. 판사 모델은 모든 좌석의 최신 입장·중요도·근거, 현재 모드와 남은 토론 횟수를 전달받는다. 충돌이 없으면 이 판단으로 최종 여행안을 확정하고 양쪽 세션에 판사 명의로 한 번 게시한다. |
| J2 · 파이터 모드 | 판사는 토론을 열고 쟁점을 알려 준다. 마감 전에 수락한 지시가 개인 발언과 제안에 반영된 뒤 판사가 전원의 최신 제안과 이전 판단을 다시 검토한다. 마지막 토론 뒤에는 추가 논의를 요청할 수 없음을 모델에 알린다. 가능한 항목은 확정하고 양립할 수 없는 필수 조건과 확인이 필요한 근거는 최종 결정에 표시한다. |
| J3 · 공개 화면 | 방 생성·사용법·협상·결과에서 판사와 개인 에이전트의 역할이 텍스트로 구분된다. 두 모드는 ‘조율 모드’, ‘파이터 모드’로 읽힌다. 공개 채팅·결정 이력·최종 결과의 판사가 일치하며, 판사의 말투와 비공개 지시 원문은 판단 모델의 입력에서 제외한다. |
| J4 · 호환성과 복구 | 기존 `mediator` 요청·응답, 프리셋과 브라우저 초안, 단계·이벤트 ID, 운영 모델 설정을 계속 읽는다. 과거 방의 시스템 발언은 공개할 때 판사로 표시하고, 참가자가 쓴 문장과 이름은 보존한다. 실패 후 재시도와 재접속으로 같은 판결이 중복되지 않는다. |

한 발언은 한 항목을 수정할 수 있다. 같은 참가자가 발언 전에 교통과 예산 등 서로 다른 항목에 지시를 둘 이상 보내면, 개인 에이전트는 접수 번호순으로 지시 하나씩 발언하고 그 번호까지 처리했다고 저장한다. 마감 뒤에도 접수된 마지막 번호까지 처리한 뒤 판사를 호출한다. 시험에서는 두 항목 모두 다음 판사 입력에 반영되는지, 마감과 재시도 뒤 각 지시에 해당하는 공개 발언이 한 번씩만 남는지 확인한다.
