# ROOM-05 · 여행방 개설과 초대 링크 공유 시험

Windows의 새 Chrome 세션에서 방을 만들고, 공유 화면에서 복사한 주소로 다른 세션이 같은 방에 입장했다. 방장은 1번, 동행은 2번 좌석을 받았다. [화면과 인수 조건](../design/travel-flow.md#room-05--방을-만들고-동행을-초대하는-흐름) · [브라우저 시험](../../tests/browser_room_sharing.py)

## 실행 환경과 재현

기준 커밋은 `fcd48ca2a03a175a124f199595df41631fe903df`다. 코드 검토를 통과한 작업 트리 16개 파일의 SHA-256 목록 해시는 시험 전후 모두 `473e0b2b32690d630128184b3c3e0ab8710490bd6e231d1132ac3d41779aac37`였다. 브라우저 시험 파일의 SHA-256은 `410553fe46ffc89f6a6dd69f8223ed9ee576215375401832d2d498ad408f1868`이다.

저장소 루트에서 다음 두 명령을 실행했다. Windows 가상환경의 Python 3.11.9, Flask 3.1.1, SQLite 3.45.1, Playwright 1.65.2, headless Chrome 157.0.8103.51을 사용했다.

```powershell
.\.venv\Scripts\python.exe tests/browser_room_sharing.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

브라우저 시험은 실행할 때마다 임시 SQLite 파일과 임의 포트의 루프백 HTTP 서버를 연다. 배포 환경에 남은 값을 재현하도록 `ROOM_CREATE_CODE=old-code`를 넣었다. 각 방문자는 독립된 쿠키 저장소를 사용한다. 마지막 좌석의 준비 제출 직후 조율 화면을 확인한 뒤 실제 그래프를 한 번 실행해 결과 화면으로 진행했다. 이때 모델과 검색 응답은 회귀 시험의 고정 데이터를 사용했다.

## 실행 결과

| 기준과 입력 | 관찰한 결과 |
| --- | --- |
| 첫 방문자가 닉네임과 기본 정원 2명으로 개설 | 코드 없이 바로 `/r/<invite>/share`가 열렸다. 새로고침 후에도 읽기 전용 입력칸에 같은 출처의 `/r/<invite>`가 보였다. |
| 360 × 740 화면, 키보드, 개인 조건 초안 | 가로 스크롤 없이 세 동작이 뷰포트 안에 있었다. Tab으로 초대 주소 → 복사 → 조건 입력 순서로 이동하고 Enter로 복사를 건너뛰었다. 개인 요청을 입력하고 다시 공유 화면을 거쳐 돌아오자 원문이 남았다. |
| 실제 클립보드 및 쓰기 거부 | 복사 버튼을 누르자 이전 클립보드 값이 공개 주소로 바뀌고 성공 문구가 상태 영역에 나타났다. 시험용 HTTP 헤더로 Chrome의 쓰기 권한을 차단하자 대체 안내가 같은 상태 영역에 표시됐다. 후속 상태 조회 두 번을 거쳐도 성공 시 버튼의 초점과 문구, 거부 시 입력칸 초점과 전체 선택 범위 및 안내가 유지됐다. |
| 다른 방문자가 방장용 주소와 복사된 주소를 차례로 열고 입장 | 방장용 주소가 공개 주소로 전환되고 API에서 방문자의 좌석은 비어 있었다. 복사한 주소에서 입장 1/2명을 확인하고 닉네임을 제출하자 양쪽 세션의 방 ID와 입장 수가 같았다. 세 번째 방문자는 마감된 버튼을 보았다. |
| 참여 상태별 복귀 | 방장이 먼저 준비한 방에서 공유 화면의 ‘대기 화면으로’가 입장 2/2명·준비 1/2명인 대기로 연결됐다. 별도 방에서 게스트가 먼저 준비한 뒤 방장용 주소를 열자 자기 대기 화면이 열렸고 공개 주소를 복사했다. 전원이 준비한 첫 방에서 두 세션 모두 방장용 주소로 조율·최종 여행안 화면을 각각 다시 열었다. |
| 서버에 저장된 생성 응답의 유실과 잘못된 초대값 | 같은 폼에서 최초 성공 응답은 전송 중 끊고, 두 번째 성공 응답의 초대값은 `bad/value`로 바꿨다. 매번 오류, 기존 닉네임, 재시도 버튼을 확인하고 쿠키를 지웠다. 세 번째 시도에서 원래 방장 좌석이 복구됐다. 서버에 도착한 세 요청의 생성 키와 본문, 발급한 초대값은 각각 동일했다. DB에는 첫 정상 방과 이 복구 방을 합쳐 정확히 2개가 있었다. |
| 일시적 조회 실패, 없는 방, 잘못된 경로 | 공유 화면 새로고침 때 첫 조회를 끊자 연결 안내가 보였다. 자동 재조회가 같은 주소를 복원했다. 없는 방은 링크 확인 안내와 ‘처음으로’가 열렸고 버튼으로 첫 화면에 도달했다. 허용하지 않는 문자를 넣은 경로는 HTTP 404였다. |
| API 경계 및 전체 회귀 | 100개 시험 통과, 건너뜀 0개, 10.033초. 동시 생성 재전송, 독립 생성·쿠키 범위, 이름·정원 검증, 타 출처 거부, 전체 방 한도 및 Render의 PostgreSQL 요구 검사가 포함됐다. [API 시험](../../tests/test_room_creation.py) |

변경 전 동작은 담당 아키텍트가 같은 기준 커밋에서 새 DB와 이전 환경값으로 확인했다. 기존 폼은 개설 코드를 요구했고, 코드 없는 유효한 생성 요청은 `403 team_code`, `/r/demo/share`는 404였다. 당시 팀 코드 요구사항 검증 기록도 보존돼 있다. [기존 통합 시험](group-travel.md)

접근성 결과는 Chrome의 키보드 동작, 접근 가능한 레이블과 상태 역할을 확인한 것이다. 실제 스크린리더 음성, 휴대전화의 시스템 선택 메뉴, 운영 Render 및 실서비스 AI 호출은 이 시험의 실행 범위 밖이다.
